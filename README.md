# Стартовый код — кейс «Граф денег»

## Financial network investigation interface

Run the interactive analyst workspace from the repository root:

```bash
streamlit run interface/network_app.py
```

The interface reads the supplied files in `parquet/` and analysis exports in `out/`. It includes an **Overview** with whole-dataset and filtered totals, an interactive **Network** with directed flows, role/cluster filters and customer focus, **Top Customers** from `top_nodes.csv`, and a **Customer Inspector** with heuristic role score, evidence, observed counterparties and flow amounts. Search exact GIDs in the sidebar; selecting a graph node, ranked row, or counterparty updates the shared customer selection. Seed incompleteness and depth-cutoff limits are called out in context.

Install the requirements first if needed: `pip install -r requirements.txt`.

Чтобы вы не тратили час из пяти на загрузку parquet и сборку графа.

## Запуск

```bash
pip install -r requirements.txt
python starter.py
```

На выходе рядом со скриптом — `out/nodes_roles.csv`, `out/clusters.csv`, `out/top_nodes.csv` в схеме из ТЗ. По умолчанию входные parquet-файлы читаются из `parquet/`; папка вывода создаётся автоматически. Пути можно переопределить через `--data` и `--out`.

## Четыре ловушки, на которых ломаются наивные решения

**1. `out_deg == 0` не значит «деньги осели».**
444 узла лежат на 4-м колене — обход просто закончился на них. Настоящий ли это конечный получатель или у него есть переводы дальше, которых нет в выгрузке, — по этим данным напрямую не видно. Придумайте, как их различить, и объясните логику.

**2. У seed-клиентов `in_kzt` занижен.**
Граф собран **от** seed по исходящим. Деньги, которые seed получил извне выборки, в данных отсутствуют. Поэтому `pass_through` у них бывает 20 и больше — это не аномалия, это устройство выгрузки. Не стройте роль на «сколько получил» для seed вслепую.

**3. Суммы и количество переводов — разные сигналы.**
Один перевод на 4 млн и сорок переводов по 100 тыс. дают одинаковый `in_kzt`, но означают разное поведение. Смотрите обе величины.

**4. Граф направленный и взвешенный.**
`nx.degree_centrality` на неориентированной проекции сотрёт всю суть кейса — направление движения денег. Если используете ненаправленные методы (например, кластеризацию), оговорите это явно.

## Правила назначения ролей

`starter.py` назначает ровно одну роль каждому gid по наблюдаемым рёбрам. Порядок правил закреплён в коде: `distributor` → `transit` → `consolidator` → `terminal` → `coordinator` → `peripheral`. Раннее правило имеет приоритет при совпадении признаков.

Пороги выбраны по фактическому распределению этой выгрузки (2 248 клиентов, 3 119 направленных пар): медиана входящей степени 1, её 95-й процентиль 3; у исходящей степени медиана 0, 75-й процентиль 1 и 95-й процентиль 5. Медиана входящих транзакций равна 1, исходящих — 0; медиана входящего оборота среди всех клиентов равна 50 000 KZT, исходящего — 0. Среди клиентов с входящим оборотом pass-through имеет 75-й процентиль 0,22 и 80-й — 0,62; порог 0,8 выше 80-го процентиля. В наборе 81 seed, 19 клиентов без рёбер и 444 клиентов глубины 4 без исходящего ребра.

- **distributor** — не менее 5 различных исходящих контрагентов. Это главный критерий роли; оборот и число переводов показаны как дополнительное свидетельство.
- **transit** — есть входящие и исходящие рёбра, клиент не seed, входящий оборот не менее 50 000 KZT и `pass_through >= 0.8`. Следовательно, наблюдаемый исходящий оборот составляет значимую долю входящего. Одного коэффициента недостаточно.
- **consolidator** — не менее 2 входящих контрагентов, не более 1 исходящего и pass-through не выше 0,5. Клиенты на глубине 4 без выхода исключены: сбор мог закончиться на них.
- **terminal** — есть входящие потоки, нет наблюдаемых исходящих рёбер, глубина меньше 4. Это гипотеза об observed endpoint, а не утверждение, что деньги действительно остались у клиента.
- **coordinator** — есть и входящие, и исходящие рёбра, но не сработало более специфичное правило. Сам факт связующей активности — слабее, чем явный транзит или распределение.
- **peripheral** — недостаточно признаков остальных ролей; сюда относятся изолированные клиенты, небольшие источники с одним получателем и нулевые по выходу клиенты на глубине 4.

`role_score` — ограниченная шкалой 0–1 **эвристическая сила поддержки назначенной роли**, не вероятность и не калиброванная уверенность. Значение выше при более выраженном паттерне (например, больше получателей или более сильные входящие связи). Для слабой периферии, изолированных клиентов и глубины-4 среза оценка специально ниже. Для seed pass-through не используется как самостоятельное основание транзита, а в evidence явно отмечена возможная неполнота входящих потоков. Каждая строка evidence приводит наблюдаемые контрагенты, число транзакций, суммы, pass-through, глубину и seed-статус; формулировки описывают гипотезы, а не правонарушения.

## Требования к выгрузкам

Схема зафиксирована в ТЗ, жюри проверяет её механически:

- `nodes_roles.csv` — ровно **2 248 строк**, все колонки заполнены, `evidence` содержит числа, а не «высокий скор»;
- `clusters.csv` — строка на кластер, включая гипотезу о его назначении;
- `top_nodes.csv` — **не менее 20** строк, отсортированных по приоритету.

Лишние колонки добавлять можно, обязательные удалять — нет.

## Интерпретация кластеров и рейтинга

Кластеры строятся алгоритмом Louvain на **неориентированной проекции** графа: веса направленных рёбер между парой клиентов складываются, поэтому направление потока при назначении сообществ теряется. Внутренний оборот `sum_kzt_internal` при этом считается по исходным направленным рёбрам, а изолированные клиенты включаются в граф как отдельные одноузловые кластеры. `top_gids` содержит до пяти участников с наибольшим суммарным внутренним инцидентным оборотом.

Гипотезы в `clusters.csv` описывают только наблюдаемые размеры, связи, обороты и распределение назначенных ролей. Они являются осторожными описаниями возможной функции группы, а не утверждениями о нарушениях.

`top_nodes.csv` ранжирует клиентов по детерминированной смеси уже рассчитываемых сигналов: `role_score` (50%), нормированный `log1p(in_kzt + out_kzt)` (30%) и нормированный взвешенный PageRank (20%). В `why` приведены те же числовые основания назначения роли из `nodes_roles.csv`, PageRank и кластер. У seed-клиентов входящие потоки могут быть неполными, поэтому их pass-through не трактуется как самостоятельное свидетельство транзита. Узлы на глубине 4 без исходящих рёбер могут быть обрезаны сбором; это не доказывает, что они являются конечными получателями.

В `nodes_roles.csv` неопределённый `pass_through` (нет наблюдаемого входящего оборота) записывается как `0` для заполненного числового экспорта; `in_deg` и `in_kzt` позволяют отличить такой случай от рассчитанного нулевого отношения. Роль и объяснение строятся одним проходом, поэтому `clusters.csv` и `top_nodes.csv` используют те же актуальные назначения и оценки.

## Подсказки по инструментам

```python
import networkx as nx

nx.pagerank(G, weight="sum_kzt")            # влияние узла
nx.hits(G)                                   # хабы и авторитеты — разделяет источники и сборщиков
nx.betweenness_centrality(G, weight=...)     # посредничество: кто «между»
nx.community.louvain_communities(UG)         # кластеры (на неориентированной проекции)
nx.simple_cycles(G, length_bound=6)          # возвратные потоки
nx.weakly_connected_components(G)            # изолированные фрагменты сети
```

`transactions.parquet` не использован в стартовом коде намеренно — там лежат даты, а временны́е паттерны дают дополнительные баллы.
